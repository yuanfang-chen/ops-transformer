# UT 覆盖率增强技能指南

本文件为 Claude Code 在 ops-transformer 仓库中进行单元测试（UT）覆盖率分析和提升提供指导。

## 项目概述

本项目是 ops-transformer 算子仓库的 UT 覆盖率增强工具，用于分析和提升算子测试用例的代码覆盖率。

### 核心功能

- 运行指定算子的 UT 并计算覆盖率
- 分析未覆盖的代码路径和分支
- 生成补充测试用例以提升覆盖率
- 重新运行 UT 并分析覆盖率提升情况
- 生成覆盖率提升报告

## 环境和前置条件

### 1. 工作目录

- **工作目录**：`ops-transformer/`
- **验证环境**：容器 `y00845930_dev`
- 所有命令需在 `ops-transformer` 目录下执行

### 2. UT 类型说明

| 类型 | 说明 | 测试内容 |
|-----|------|---------|
| **ophost** | Host 侧测试 | 算子 tiling 和 infershape 的测试用例 |
| **opapi** | API 接口测试 | 算子 ACLNN 接口的测试用例 |
| **opkernel** | Kernel 侧测试 | 算子 kernel 的测试用例 |
| **opgraph** | 图模式测试 | 暂不支持 |

### 3. 编译运行命令

```bash
# 进入 ops-transformer 目录
cd ops-transformer

# 编译运行单类型 UT 并获取覆盖率报告
bash build.sh -u --ophost --ops="算子名称" --cov

# 编译运行 opapi UT
bash build.sh -u --opapi --ops="算子名称" --cov

# 编译运行 opkernel UT
bash build.sh -u --opkernel --ops="算子名称" --cov

# 编译运行所有类型 UT
bash build.sh -u --ops="算子名称" --cov
```

### 4. 调试环境变量

设置以下环境变量可以在运行 UT 时把 Ascend 日志打屏，便于调试：

```bash
export ASCEND_SLOG_PRINT_TO_STDOUT=1
export ASCEND_GLOBAL_LOG_LEVEL=0
```

## 核心职责与原则

### 核心职责

1. 分析算子 UT 的代码覆盖率，识别未覆盖的代码路径
2. 设计并实现补充测试用例，提升覆盖率
3. 验证测试用例的有效性，确保新增用例能真正提升覆盖率
4. 生成详细的覆盖率提升报告

### 核心原则 ⭐

> **UT 覆盖率提升 ≠ 盲目增加测试用例数量**
>
> 目标是通过有针对性的测试用例设计，覆盖关键代码路径和边界条件，而不是简单地堆砌用例。

**测试设计原则**：

| 原则 | 说明 | 示例 |
|-----|------|------|
| **边界优先** | 优先测试边界值和极值 | 最小/最大形状、0值、空tensor |
| **路径完整** | 覆盖所有代码分支 | if/else各分支、异常处理路径 |
| **场景多样** | 测试不同参数组合 | 不同数据类型、不同shape组合 |
| **独立性** | 新增用例独立可运行 | 不依赖其他用例的执行结果 |

**常见误区**：

| 误区 | 正确做法 |
|-----|---------|
| 随意增加测试数据大小 | 分析未覆盖代码，有针对性设计 |
| 只关注行覆盖率 | 同时关注分支覆盖率和条件覆盖率 |
| 忽略异常路径 | 补充错误处理和边界条件测试 |
| 修改原测试用例 | 新增用例独立添加，不破坏原有测试 |

## 各阶段详细指南

### 阶段一：需求充分性检查

在开始 UT 覆盖率增强前，确认以下信息是否完整：

#### 必需信息（缺失则进入 Interview 模式）
- [ ] **算子名称**：明确要增强哪个算子的 UT 覆盖率
- [ ] **UT 类型**：ophost、opapi、opkernel 或全部
- [ ] **目标覆盖率**（可选）：期望达到的覆盖率目标

#### Interview 模式触发条件
当用户输入满足以下任一条件时，使用 **AskUserQuestion** 工具主动提问：

1. **缺少算子名称**：未指定要处理哪个算子
2. **缺少 UT 类型**：未指定要处理哪种类型的测试
3. **信息模糊**：如"提升覆盖率"但未说明具体算子和类型

**✓ 检查清单**：
- [ ] 算子名称已确认
- [ ] UT 类型已确认
- [ ] 目标覆盖率已明确（如需）

### 阶段二：覆盖率配置检查

在运行 UT 前，**必须检查**覆盖率配置是否正确。

#### 1. 检查 test_config.yaml

查看算子在 `tests/test_config.yaml` 中的配置：

```yaml
# 示例：all_gather_matmul 的配置
mc2:
  matrix:
    all_gather_matmul:
      module: True
      src:
        - mc2/all_gather_matmul
        - mc2/common
      exclude:
        - mc2/all_gather_matmul/docs
        - mc2/all_gather_matmul/README.md
      ut_cov_exclude:
        - mc2/all_gather_matmul  # 如果整个目录被排除，则不会统计覆盖率
      test:
        examples: False
      options:
        - all_gather_matmul
```

#### 2. 配置检查要点

- `ut_cov_exclude` 下的目录**不会被统计覆盖率**
- 如果需要统计覆盖率，确保相关源码目录未被排除
- 全局配置中 `global_config.ut_cov_exclude` 排除 `*/tests/*`、`*/third_party/*` 等

#### 3. 配置问题处理

如果发现 `ut_cov_exclude` 排除了需要统计的源码目录：
- **方式1**：修改配置文件，移除相关排除项
- **方式2**：说明由于配置限制无法统计该部分的覆盖率

**✓ 检查清单**：
- [ ] 已检查 test_config.yaml 配置
- [ ] 确认需要统计的目录未被 ut_cov_exclude 排除
- [ ] 已记录初始配置状态

### 阶段三：运行初始UT并获取覆盖率

#### 1. 运行 UT 并保存日志

```bash
# 运行 UT 并获取覆盖率，同时保存日志
bash build.sh -u --ophost --ops="算子名称" --cov > /output/cov_log/算子名称/original_cov.log 2>&1
```

#### 2. 解析覆盖率报告

命令执行完后，会生成详细的 HTML 格式覆盖率报告：

- **报告位置**：`build/cov_result/html_report/`
- **关注指标**：
  - 行覆盖率（Line Coverage）：主要指标
  - 分支覆盖率（Branch Coverage）
  - 函数覆盖率（Function Coverage）

#### 3. 记录初始状态

记录以下信息：
- 当前覆盖率百分比
- 主要未覆盖的代码模块
- 未覆盖的关键函数

**✓ 检查清单**：
- [ ] UT 运行成功
- [ ] 覆盖率报告已生成
- [ ] 已记录初始覆盖率数据
- [ ] 已识别主要未覆盖模块

### 阶段四：分析未覆盖代码

#### 1. 获取详细覆盖率信息

使用 `lcov` 工具生成详细报告：

```bash
# 生成覆盖率报告
lcov --capture --directory build --output-file coverage.info
genhtml coverage.info --output-directory coverage_html
```

#### 2. 分析未覆盖代码路径

从 HTML 报告中分析：

| 分析维度 | 检查内容 |
|---------|---------|
| **未覆盖函数** | 哪些函数完全没有被测试覆盖 |
| **未覆盖分支** | if/else 条件分支的覆盖情况 |
| **未覆盖行** | 具体哪些代码行未被执行 |
| **边界条件** | 边界值、极值的测试是否缺失 |
| **异常路径** | 错误处理、异常情况的测试是否缺失 |

#### 3. 定位测试文件

根据 UT 类型，定位测试文件位置：

| UT 类型 | 测试文件位置 |
|---------|-------------|
| ophost | `mc2/算子名称/tests/ut/op_host/` |
| opapi | `mc2/算子名称/tests/ut/op_api/` |
| opkernel | `mc2/算子名称/tests/ut/op_kernel/` |

**✓ 检查清单**：
- [ ] 已生成详细覆盖率报告
- [ ] 已识别未覆盖的函数和分支
- [ ] 已定位测试文件位置
- [ ] 已分析现有测试用例覆盖场景

### 阶段五：设计补充测试用例

#### 1. 测试场景补充策略

根据 UT 类型，采用不同的补充策略：

##### ophost 测试场景

| 场景类别 | 测试内容 | 示例 |
|---------|---------|------|
| **Tiling 参数** | 不同输入形状组合 | 小/中/大shape、不规则shape |
| **InferShape** | 各种输入形状推导 | 动态维度、rank变化、空tensor |
| **多卡场景** | 分布式参数 | 不同rank、不同通信模式 |

##### opapi 测试场景

| 场景类别 | 测试内容 | 示例 |
|---------|---------|------|
| **参数验证** | 空指针、无效参数 | nullptr检查、越界检查 |
| **Workspace** | workspace大小获取 | 最小/最大workspace |
| **正常流程** | 各种数据类型 | float16、float32、int32 |

##### opkernel 测试场景

| 场景类别 | 测试内容 | 示例 |
|---------|---------|------|
| **计算逻辑** | 不同数据类型 | fp32、fp16、int8 |
| **边界值** | 特殊值测试 | 0、NaN、Inf、最大/最小值 |
| **性能路径** | 不同数据量 | 小数据量 vs 大数据量 |

#### 2. 测试用例设计要点

| 设计要点 | 说明 |
|---------|------|
| **边界优先** | 最小值、最大值、0值、空tensor |
| **路径完整** | 覆盖所有 if/else 分支 |
| **异常处理** | 测试错误处理和异常情况 |
| **参数组合** | 不同数据类型、shape组合 |

**✓ 检查清单**：
- [ ] 已分析未覆盖代码的触发条件
- [ ] 已设计针对性的测试场景
- [ ] 已明确每个测试用例的目的

### 阶段六：实现测试用例

- [ ] 测试用例已添加明确注释
- [ ] 测试用例命名符合规范
- [ ] 测试用例可独立运行

## 重要注意事项

### 1. 配置检查优先原则 ⭐⭐⭐

> **始终先检查 test_config.yaml 配置**
>
> 在分析覆盖率前，必须确认算子的 `ut_cov_exclude` 配置是否正确排除/包含需要统计的源码目录。

**检查要点**：
- 确认需要统计覆盖率的源码目录未被 `ut_cov_exclude` 排除
- 了解全局 `global_config.ut_cov_exclude` 的排除规则
- 如果配置不合理，先修正配置或说明限制

### 2. 增量开发原则

> **一次补充一个测试场景，逐步验证**
>
- 先设计并实现一个测试场景
- 运行 UT 验证有效性
- 再继续下一个场景
- 避免一次性添加大量测试用例导致调试困难

### 3. 测试独立性原则

> **新增测试用例应独立可运行**
>
- 不依赖其他用例的执行顺序
- 不依赖外部状态
- 每个用例独立设置和清理

### 4. 文档记录原则

> **记录每个测试用例的目的和覆盖场景**
>
- 在测试用例前添加明确注释
- 说明测试场景和覆盖的代码位置
- 便于后续维护和审查

## 常见问题与处理

### 问题1：覆盖率报告未生成

**可能原因**：
- UT 运行失败
- 配置文件错误
- 编译错误

**处理方式**：
1. 检查 UT 运行日志，确认是否通过
2. 检查 `test_config.yaml` 配置
3. 检查编译是否成功

### 问题2：覆盖率数据不完整

**可能原因**：
- 源码目录被 `ut_cov_exclude` 排除
- 源码文件不在统计范围内

**处理方式**：
1. 检查 `test_config.yaml` 配置
2. 确认需要统计的目录未被排除
3. 如无法修改配置，说明限制

### 问题3：新增测试用例后覆盖率未提升

**可能原因**：
- 测试用例未真正触发未覆盖代码
- 代码路径为不可达代码（死代码）
- 测试用例执行失败

**处理方式**：
1. 检查测试用例是否通过
2. 分析未覆盖代码的触发条件
3. 确认代码是否可达

### 问题4：测试用例执行失败

**可能原因**：
- 测试数据设置不当
- 测试逻辑错误
- 依赖环境问题

**处理方式**：
1. 检查测试数据是否正确
2. 使用调试环境变量查看日志
3. 确认测试环境配置正确

## 开发失败处理

当遇到无法解决的覆盖率提升问题时：

1. **记录失败原因**：
   - 明确说明哪些代码无法覆盖
   - 记录已尝试的测试场景和结果
   - 提供相关配置或环境限制说明

2. **诚实报告**：
   - 不要强行增加无效测试用例
   - 明确标注"覆盖率无法提升"及原因
   - 说明是配置限制、技术限制还是代码本身问题

3. **提供改进建议**：
   - 建议可能的配置调整
   - 建议代码优化方向
   - 建议测试环境改进
