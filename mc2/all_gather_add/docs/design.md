# AllGatherAdd 设计文档

## 1. 设计目标

### 1.1 背景

`all_gather_add` 是一个 MC2 融合算子，目标是在单次算子执行中完成通信与逐元素计算融合，并同时保留 gather 结果与计算结果。该算子不面向图模式，不要求多架构特化实现，当前仅针对冻结规格给出首版实现设计。

### 1.2 设计目标

本设计需满足以下目标：

1. 实现 `AllGather(A)` 与 `A_gathered + B` 的融合处理；
2. 输出两个结果：
   - 输出1：`A_gathered`
   - 输出2：`C`
3. 在一次算子执行内部完成由 `commTurn` 驱动的轮次处理；
4. 每轮处理一半数据，形成清晰的流水结构；
5. 首版优先保证语义正确、结构清晰、便于验证与后续优化；
6. 不依赖复用现有算子实现逻辑，但允许参考同类算子的工程组织方式。

### 1.3 非目标

以下内容不属于本次设计目标：

- 图模式支持
- 动态 shape 通用化
- 多 dtype 扩展
- 多 rank 规模扩展
- 特定架构专门实现
- 首版极致 overlap 优化

## 2. 冻结规格

### 2.1 输入

#### 输入1：`A`
- shape：`[1024, 2048]`
- dtype：`FP16`
- format：`ND`

#### 输入2：`B`
- shape：`[2048, 2048]`
- dtype：`FP16`
- format：`ND`

### 2.2 属性

#### `group`
- 类型：通信域配置项
- 作用：指定该算子的 HCCL 通信域
- 约束：作为既定接口参数处理，不展开底层实现细节

### 2.3 输出

#### 输出1：`A_gathered`
- 语义：`AllGather(A)`
- shape：`[2048, 2048]`
- dtype：`FP16`
- format：`ND`

#### 输出2：`C`
- 语义：`C = A_gathered + B`
- shape：`[2048, 2048]`
- dtype：`FP16`
- format：`ND`

### 2.4 通信规模

- rank 数固定为 `2`

因此：
- 每卡持有本地 `A_local.shape = [1024, 2048]`
- 沿第 0 维做 `AllGather` 后：
  - `A_gathered.shape = [1024 * 2, 2048] = [2048, 2048]`

## 3. 语义定义

### 3.1 数学语义

设 2 卡上的输入分别为：

- rank0 上本地输入：`A0`
- rank1 上本地输入：`A1`

则标准 AllGather 后：

```text
A_gathered =
[
  A0
  A1
]
```

其中：
- `A0.shape = [1024, 2048]`
- `A1.shape = [1024, 2048]`
- `A_gathered.shape = [2048, 2048]`

最终加法输出为：

```text
C = A_gathered + B
```

其中 `B.shape = [2048, 2048]`，与 `A_gathered` 逐元素对齐。

### 3.2 双输出定义

输出顺序固定为：

1. 输出1：`A_gathered`
2. 输出2：`C`

该顺序属于接口契约的一部分，不应在实现中交换。

### 3.3 当前冻结输入下的轮次流水定义

单算子内部执行轮次由 `commTurn` 决定。在当前冻结输入中，`commTurn = 2`，因此本设计中的轮次定义为：

- 一次算子执行内分成两轮；
- 每轮处理每个 rank 本地 `A` 的一半数据；
- 每轮都必须独立完成：
  - gather 对应块的数据形成 / 落位
  - 与 `B` 对应块做加法
  - 将结果写入 `C` 对应块

该定义要求实现具备“按轮处理”的真实结构，而不是仅保留一个名义上的参数。后续若扩展 `commTurn` 支持范围，应保持这一语义不变。

## 4. 两轮分块设计

### 4.1 分块原则

首版推荐沿每个 rank 的本地 shard 在第 0 维均分：

- 每个 rank 的本地 `A` 为 `[1024, 2048]`
- 每轮处理每个 rank 的 512 行
- 两个 rank 在每轮合计处理 1024 行全局结果
- 共 2 轮

原因：
- 与 2 卡场景天然一致；
- 切分简单、偏移明确；
- 便于验证 gather 顺序和 `B` 的对应关系；
- Host/Tiling/Kernel 表达成本最低。

### 4.2 推荐分块示意

#### 每轮 Gather 的全局落位

```text
Round 0:
  rank0 local A[0:512,    :] -> A_gathered[0:512,    :]
  rank1 local A[0:512,    :] -> A_gathered[1024:1536, :]

Round 1:
  rank0 local A[512:1024, :] -> A_gathered[512:1024,  :]
  rank1 local A[512:1024, :] -> A_gathered[1536:2048, :]
```

#### B 按相同全局区间参与

```text
Round 0 使用:
  B[0:512,    :]
  B[1024:1536, :]

Round 1 使用:
  B[512:1024,  :]
  B[1536:2048, :]
```

#### C 按相同全局区间写回

```text
Round 0 输出:
  C[0:512,    :]
  C[1024:1536, :]

Round 1 输出:
  C[512:1024,  :]
  C[1536:2048, :]
```

### 4.3 轮次级数据关系

#### Round 0
- gathered 区间：`A_gathered[0:512, :]` 与 `A_gathered[1024:1536, :]`
- B 区间：`B[0:512, :]` 与 `B[1024:1536, :]`
- 输出区间：`C[0:512, :]` 与 `C[1024:1536, :]`

#### Round 1
- gathered 区间：`A_gathered[512:1024, :]` 与 `A_gathered[1536:2048, :]`
- B 区间：`B[512:1024, :]` 与 `B[1536:2048, :]`
- 输出区间：`C[512:1024, :]` 与 `C[1536:2048, :]`

### 4.4 顺序约束

每轮中必须保证：
1. 该轮 gather 对应数据已经可用；
2. `A_gathered` 对应块已正确落位；
3. Add 仅消费该轮对应块；
4. 本轮输出写入对应区间；
5. 不得跨轮混用数据。

## 5. 总体架构设计

### 5.1 模块划分

建议算子工程按以下模块组织：

- 算子定义 / 注册
- Host 校验与 shape/dtype 推导
- API 两段式调用
- Tiling 设计与生成
- Kernel 主实现
- 构建配置
- 测试
- 文档与示例

可查阅 `mc2/all_gather_matmul` 的模块组织方式，但本设计不依赖其具体实现逻辑。

### 5.2 职责分工总览

| 模块 | 主要职责 |
|------|----------|
| 算子定义/注册 | 定义输入输出属性，绑定 `group`，声明双输出 |
| Host | 校验固定规格，推导双输出 shape/dtype |
| API | 封装两段式调用，完成 workspace 查询与执行 |
| Tiling | 固定两轮切分、偏移、buffer 需求 |
| Kernel | 按两轮完成 gather 与 add，生成双输出 |
| 测试 | 校验接口、轮次、输出正确性 |
| 文档 | 固化需求、设计和使用方式 |

## 6. Host 设计

### 6.1 Host 输入输出契约

Host 层应固定以下契约：

#### 输入
- `A`: `[1024, 2048]`, `FP16`, `ND`
- `B`: `[2048, 2048]`, `FP16`, `ND`

#### 属性
- `group`

#### 输出
- `A_gathered`: `[2048, 2048]`, `FP16`, `ND`
- `C`: `[2048, 2048]`, `FP16`, `ND`

### 6.2 Host 校验项

建议 Host 层至少校验：

1. 输入个数正确；
2. 输出个数正确；
3. `A`、`B`、输出均为 `ND`；
4. `A`、`B`、输出均为 `FP16`；
5. `A.shape == [1024, 2048]`；
6. `B.shape == [2048, 2048]`；
7. `A_gathered.shape == [2048, 2048]`；
8. `C.shape == [2048, 2048]`；
9. 通信规模为 2 卡；
10. `group` 非空且可用。

### 6.3 输出推导

在固定 2 卡前提下：

- `A_gathered.dim0 = A.dim0 * 2 = 2048`
- `A_gathered.dim1 = A.dim1 = 2048`
- `C.shape = A_gathered.shape = B.shape = [2048, 2048]`

### 6.4 Host 侧设计要求

- 输出顺序必须固定；
- 双输出不可省略；
- 由 `commTurn` 驱动的轮次处理语义应固化为 tiling 生成的前提；当前版本仅支持 `commTurn = 2`；
- 不引入图模式相关逻辑；
- 不引入架构分支定制。

## 7. API 设计

### 7.1 API 形态

推荐采用标准两段式接口模型：

#### 第一段
职责：
- 参数校验
- workspace 大小计算
- executor 构造
- 双输出签名绑定

#### 第二段
职责：
- 根据 executor 和 workspace 实际发起执行

### 7.2 API 输入输出语义

#### 输入
- `A`
- `B`
- `group`

#### 输出
- 输出1：`A_gathered`
- 输出2：`C`

### 7.3 API 校验重点

建议 API 层重点增加以下约束：

1. 输出1 与输出2 必须是独立输出；
2. 不允许输出地址别名或重叠；
3. 输入输出 dtype 一致；
4. 输入输出 shape 与冻结规格一致；
5. `group` 合法；
6. 不支持图模式相关扩展参数。

### 7.4 API 设计原则

- 接口应尽量贴近冻结需求，不引入不必要的可选项；
- 若工程规范要求保留更多参数，也应对其做强约束，确保不偏离冻结语义；
- 输出顺序和输出语义必须清晰写入文档。

## 8. Tiling 设计

### 8.1 设计目标

Tiling 侧需要明确表达：

- 总轮次：`2`
- 每轮每个 rank 处理行数：`512`
- 每轮全局处理总行数：`1024`
- 每轮输出1偏移
- 每轮输出2偏移
- 每轮 `B` 偏移
- 是否需要 staging buffer
- 是否使用双缓冲

### 8.2 首版推荐 Tiling 常量

建议按固定规格直接固化以下信息：

- `round_num = 2`
- `rows_per_rank_per_round = 512`
- `global_rows_per_round = 1024`
- `cols = 2048`
- `dtype = FP16`
- `elem_size = 2 bytes`

### 8.3 每轮数据量

每轮块大小：

```text
单个 rank 半块：
512 * 2048 * 2 bytes = 2,097,152 bytes = 2 MB

单轮全局总量：
2 * 512 * 2048 * 2 bytes = 4,194,304 bytes = 4 MB
```

因此：
- `A_gathered` 每轮总处理量约 4 MB，由两个 2 MB 区间组成
- `B` 每轮总读取量约 4 MB，由两个 2 MB 区间组成
- `C` 每轮总写回量约 4 MB，由两个 2 MB 区间组成

### 8.4 偏移表达建议

建议 Tiling 中明确以下逻辑字段：

- 当前轮索引 `round_idx`
- 当前轮 rank 内起始行 `local_row_start`
- 当前轮 rank 内结束行 `local_row_end`
- 当前轮两个全局落位区间
- `A_gathered` 写入偏移
- `B` 读取偏移
- `C` 写入偏移
- 当前轮元素数 / 字节数

### 8.5 是否需要更细粒度 tile

首版不强制要求继续在每轮内部做复杂细 tile。
推荐先以“轮”为一级切分单位，保证：

- 轮次语义真实存在；
- 每轮数据范围清晰；
- 后续如需继续细分，可在轮内增加更小 tile。

## 9. Kernel 设计

### 9.1 Kernel 总体流程

Kernel 需在一次执行中完成由 `commTurn` 驱动的轮次处理。对当前版本而言，`commTurn = 2`，推荐抽象为：

```text
for round in [0, 1]:
    1. 处理该轮 gather 数据
    2. 将 gather 结果写入 A_gathered 对应块
    3. 读取 B 对应块
    4. 计算该轮 C 对应块
    5. 完成该轮同步
```

### 9.2 每轮逻辑语义

#### Round 0
- 目标区间：`[0:512, :]` 与 `[1024:1536, :]`
- Gather 结果写入：`A_gathered[0:512, :]` 与 `A_gathered[1024:1536, :]`
- B 读取：`B[0:512, :]` 与 `B[1024:1536, :]`
- Add 输出：`C[0:512, :]` 与 `C[1024:1536, :]`

#### Round 1
- 目标区间：`[512:1024, :]` 与 `[1536:2048, :]`
- Gather 结果写入：`A_gathered[512:1024, :]` 与 `A_gathered[1536:2048, :]`
- B 读取：`B[512:1024, :]` 与 `B[1536:2048, :]`
- Add 输出：`C[512:1024, :]` 与 `C[1536:2048, :]`

### 9.3 双输出组织策略

推荐优先采用以下组织方式：

#### 方案 A：直接落到输出1
- Gather 结果直接写入 `A_gathered` 对应块
- Add 直接从 `A_gathered` 该块读取
- Add 结果写入 `C` 对应块

优点：
- 输出1 直接成为最终结果；
- 无需全量额外 gather 中间缓冲；
- 生命周期清晰；
- 双输出关系直接。

#### 方案 B：单块 staging buffer
若通信实现要求先落临时区，则每轮使用一个单块缓冲：

1. gather -> staging buffer
2. staging -> `A_gathered` 对应块
3. staging + `B` 对应块 -> `C` 对应块

适用场景：
- 直接落到输出1不方便或不安全时

#### 方案 C：双缓冲
若后续追求更高 overlap，可扩展为：
- ping / pong 两个轮级缓冲

首版不是必需项。

### 9.4 首版推荐 Kernel 策略

首版推荐：
- 保持由 `commTurn` 驱动的轮次处理结构；当前版本体现为两轮；
- 每轮内部先保证 gather 数据可用，再执行 add；
- 不强制跨轮 overlap；
- 优先实现清晰、可验证、可演进的流程。

## 10. Buffer 与 Workspace 设计

### 10.1 设计原则

- 优先减少全量中间缓冲；
- 优先保证双输出独立；
- 优先保证每轮生命周期清晰；
- 便于后续演进为双缓冲。

### 10.2 推荐 Buffer 策略

#### 优先策略
尽量采用“输出1直写”：

- gather 直接落到 `A_gathered` 对应块；
- `C` 独立输出；
- 不额外分配全量 gather buffer。

#### 备选策略
若需要中间缓冲，建议只使用单轮大小缓冲：
- 大小约 4 MB
- 用于当前轮 gather 暂存

不建议首版直接申请全量 `[2048,2048]` 临时 gather 区。

### 10.3 Workspace 关注点

workspace 主要关注：

1. 通信相关临时区；
2. 当前轮 gather staging buffer；
3. 同步元数据或控制信息；
4. 后续若引入双缓冲时的第二块轮级缓冲。

### 10.4 生命周期约束

- 若使用 staging buffer，则其生命周期应以“轮”为界；
- 下一轮开始前，必须保证上一轮已完成消费；
- 若使用双缓冲，则必须显式区分 ping / pong 的使用时机。

## 11. 同步策略设计

### 11.1 同步目标

同步策略需要保证：

1. gather 结果在本轮 add 前已就绪；
2. 本轮输出写入完成后，下一轮不会错误覆盖相关临时区；
3. 双输出对应块在写回时不存在竞争和交叉覆盖。

### 11.2 首版同步原则

首版建议采用保守同步：

- 每轮内部在 gather 数据可用后再启动 add；
- 每轮结束后确认本轮输出已完成；
- 再进入下一轮。

该策略可牺牲部分极致性能，但有利于：
- 减少调试复杂度；
- 降低数据污染风险；
- 快速建立稳定正确版本。

### 11.3 后续优化方向

后续若需要提升性能，可在保持两轮逻辑不变的前提下尝试：
- 跨轮 overlap
- 双缓冲
- 更细粒度的轮内 tile 与事件推进

但这些不属于首版强制范围。

## 12. 错误与边界处理设计

### 12.1 参数错误
应拒绝以下场景：

- `A` shape 不是 `[1024,2048]`
- `B` shape 不是 `[2048,2048]`
- 输出 shape 不匹配
- dtype 不是 `FP16`
- format 不是 `ND`
- 输出个数不是 2
- `group` 无效
- 非 2 卡通信规模

### 12.2 输出别名错误
应显式禁止：
- `A_gathered` 与 `C` 使用同一片输出内存
- 输出与不允许别名的临时区重叠

### 12.3 轮次逻辑错误
应重点防止：
- 前后块顺序交换
- 同轮偏移错位
- 本轮读取了另一轮 `B`
- 后一轮覆盖前一轮临时数据

## 13. 测试设计

### 13.1 测试目标

测试需验证：

1. 双输出语义正确；
2. 两轮结构下的前后半块均正确；
3. Gather 顺序正确；
4. `B` 分块对应关系正确；
5. 不存在轮次间污染或覆盖；
6. 首版流水结构真实存在。

### 13.2 分层测试建议

#### Host 测试
覆盖：
- shape 校验
- dtype 校验
- format 校验
- 双输出推导
- 固定规格限制

#### API 测试
覆盖：
- 双输出签名
- `group` 参数
- workspace 查询
- 输出 shape 不匹配拒绝
- 输出别名拒绝

#### Kernel 测试
覆盖：
- 当前 `commTurn = 2` 场景下的两轮处理逻辑
- 每轮偏移
- 每轮加法对应区间
- 同步顺序

#### 端到端功能测试
覆盖：
- 2 卡环境
- 固定规格输入
- 双输出校验
- Round 0 / Round 1 对应区间分别校验

### 13.3 推荐测试数据构造

为便于发现 gather 顺序和 B 分块错误，建议使用以下构造方式：

#### A 的构造
- rank0:
  - `A0[row, col] = 1 + (row % 4)`
- rank1:
  - `A1[row, col] = 101 + (row % 4)`

#### B 的构造
- `B[0:512, :] = 10`
- `B[512:1024, :] = 20`
- `B[1024:1536, :] = 30`
- `B[1536:2048, :] = 40`

#### 期望结果
- `A_gathered[0:512, :] = A0[0:512, :]`
- `A_gathered[512:1024, :] = A0[512:1024, :]`
- `A_gathered[1024:1536, :] = A1[0:512, :]`
- `A_gathered[1536:2048, :] = A1[512:1024, :]`
- `C[0:512, :] = A0[0:512, :] + 10`
- `C[512:1024, :] = A0[512:1024, :] + 20`
- `C[1024:1536, :] = A1[0:512, :] + 30`
- `C[1536:2048, :] = A1[512:1024, :] + 40`

该构造可以直接暴露：
- Gather 顺序是否正确；
- 每轮两个全局区间是否串位；
- B 是否按正确轮次参与加法；
- 是否存在轮次污染。

### 13.4 FP16 比较策略

由于推荐使用可精确表示的模式值，最小功能测试中可优先按精确值比较。
若后续扩展到更复杂数据，再引入合理误差阈值。

### 13.5 最小性能验证建议

首版不以性能为阻塞项，但建议至少做以下轻量验证：

- 实现中存在明确的两轮结构；
- 每轮都发生对应块处理；
- 不是“先完整 gather，再整体 add”的伪流水；
- 未引入不必要的全量复制。

## 14. 风险分析与规避

### 14.1 双输出风险
#### 风险
- 输出1和输出2写入区域重叠；
- gather 结果被后续 add 或临时缓冲逻辑覆盖。

#### 规避
- 输出1 / 输出2 独立管理；
- 文档与接口中明确禁止别名；
- 输出1仅作为最终 gather 结果使用。

### 14.2 两轮切分风险
#### 风险
- round0 / round1 在每个 rank 内的 512 行边界错误；
- 偏移计算不一致。

#### 规避
- 固定 `rows_per_rank_per_round = 512`；
- 统一由 tiling 数据表达偏移；
- 测试中单独验证四个全局区间。

### 14.3 Gather 落位风险
#### 风险
- rank0 / rank1 的落位顺序颠倒；
- gathered 数据写错块。

#### 规避
- 明确以标准 AllGather rank 顺序组织；
- 使用区分度明显的 rank 数据模式。

### 14.4 B 分块错配风险
#### 风险
- Round 0 使用了错误的 `B` 全局区间
- Round 1 使用了错误的 `B` 全局区间

#### 规避
- `B` 与 gathered 输出采用完全一致的全局落位区间；
- 在测试中让四段区间具有显著不同值。

### 14.5 同步风险
#### 风险
- gather 未完成就执行 add；
- staging buffer 被下一轮提前复用。

#### 规避
- 首版采用保守同步；
- 明确每轮完成条件；
- 缓冲生命周期严格按轮管理。

### 14.6 伪流水风险
#### 风险
- 实现仅保留轮次名义，实际没有按轮通信与计算。

#### 规避
- Tiling、Kernel、测试三层同时体现轮次结构；
- 验证时检查每轮对应块是否独立产生。

## 15. 实施建议

### 15.1 首版实现建议
建议按以下顺序推进：

1. 固定 Host 契约与双输出定义；
2. 固定 API 双输出签名；
3. 固定 Tiling 两轮分块；
4. 明确输出1直写或单块 staging 的 buffer 方案；
5. 完成 Kernel 轮次处理；当前版本先完成 `commTurn = 2` 的两轮处理；
6. 完成分层测试与端到端验证；
7. 完成文档收敛。

### 15.2 首版复杂度控制建议
为降低首版风险，建议避免以下做法：
- 同时引入多种轮内 tile 策略；
- 同时引入跨轮 overlap 和双缓冲；
- 扩展到动态图或多规格支持；
- 引入架构专用分支。

## 16. 结论

`all_gather_add` 的首版设计已具备明确、可实施的技术路线：

- 固定双输出：`A_gathered`、`C`
- 固定公式：`C = A_gathered + B`
- 固定规格：
  - `A=[1024,2048]`
  - `B=[2048,2048]`
  - 输出均为 `[2048,2048]`
  - 2卡
  - FP16
  - ND
  - `group`
- 单次执行内部轮次由 `commTurn` 决定；当前版本仅支持 `commTurn = 2`
- 固定每轮处理一半数据：
  - Round 0：`0:512` 与 `1024:1536`
  - Round 1：`512:1024` 与 `1536:2048`

该设计优先保证：
- 语义准确
- 双输出清晰
- 两轮结构真实
- 易于验证
- 便于后续性能优化扩展
