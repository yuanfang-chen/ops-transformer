# AllGatherAdd 规划文档

## 1. 基本信息

- 算子名称：`all_gather_add`
- 算子类名：`AllGatherAdd`
- 宏名建议：`ALL_GATHER_ADD`
- 目标场景：MC2 场景下的通信与逐元素计算融合，单次执行内完成 `AllGather(A)` 与 `A_gathered + B`，并同时输出 gather 结果与加法结果
- 开发模式：仅做 MC2 算子开发，不需要图模式，不需要特定架构专门实现

## 2. 需求冻结

### 2.1 功能冻结

本算子功能已冻结为：

1. 对输入矩阵 `A` 执行 `AllGather` 通信；
2. 生成输出1：`A_gathered = AllGather(A)`；
3. 将 `A_gathered` 与矩阵 `B` 做逐元素加法；
4. 生成输出2：`C = A_gathered + B`。

该算子为双输出算子，最终语义已固定，不再接受退化为单输出版本。

### 2.2 输入输出冻结

#### 输入
- 输入1：`A`
  - shape：`[1024, 2048]`
  - dtype：`FP16`
  - format：`ND`
- 输入2：`B`
  - shape：`[2048, 2048]`
  - dtype：`FP16`
  - format：`ND`

#### 属性
- `group`
  - 用于指定通信域
  - 在算子定义中作为既定接口/配置项处理
  - 本规划不展开其底层实现细节

#### 输出
- 输出1：`A_gathered`
  - 语义：`AllGather(A)`
  - shape：`[2048, 2048]`
  - dtype：`FP16`
  - format：`ND`
- 输出2：`C`
  - 语义：`A_gathered + B`
  - shape：`[2048, 2048]`
  - dtype：`FP16`
  - format：`ND`

### 2.3 通信规模冻结

- 参与通信卡数固定为：`2`
- 因此本地输入 `A` 为单卡分片 `[1024, 2048]`
- 在 2 卡 `AllGather` 后，沿第 0 维聚合得到：
  - `A_gathered.shape = [1024 * 2, 2048] = [2048, 2048]`

### 2.4 当前冻结输入下的轮次流水语义

单算子内部执行轮次由输入参数 `commTurn` 决定。

当前冻结输入中，`commTurn = 2`，其含义已冻结为：

- 不是测试中连续调用两次算子；
- 而是单次算子执行内部，将 `AllGather + Add` 流程拆为 2 轮；
- 每轮处理每张卡本地 `A` 的一半数据，形成分段式通信与计算结构；
- 第一轮处理各 rank 本地 `A` 的前 512 行，对应全局输出区间 `0:512` 与 `1024:1536`；
- 第二轮处理各 rank 本地 `A` 的后 512 行，对应全局输出区间 `512:1024` 与 `1536:2048`。

本语义要求必须体现在 Host/Tiling/Kernel 设计中，不能被实现为“先完整 gather，再整体 add”的伪流水。

## 4. 方案概述

### 4.1 总体思路

算子采用“通信与逐元素计算融合”的实现方式，整体分为以下职责层次：

- Host 层
  - 定义算子签名与约束
  - 校验固定规格
  - 推导双输出 shape / dtype
  - 固化 2 卡、FP16、ND、双输出，以及当前版本仅支持 `commTurn = 2` 的前提

- API 层
  - 提供两段式调用接口
  - 第一段完成参数校验、workspace 估算、executor 构造
  - 第二段完成实际执行

- Tiling 层
  - 固定两轮分块策略
  - 明确每轮处理范围、偏移与缓冲需求
  - 为 Kernel 提供轮次级调度参数

- Kernel 层
  - 在单次执行内部完成 2 轮处理
  - 每轮执行：通信、数据落位、逐元素加法、必要同步
  - 输出 `A_gathered` 与 `C`

### 4.2 推荐技术路线

首版建议采用保守而清晰的实现路线：

- 沿每个 rank 的本地 `A` 按第 0 维切成两半；
- 每轮 gather 所有 rank 的同序半块；
- 每轮在全局 `A_gathered` / `B` / `C` 上处理两个不连续区间；
- 优先保证两轮结构、双输出语义和数据正确性；
- 首版允许只保留“逻辑上的流水结构”，不强求极致 overlap；
- 后续若性能需要，再演进为更强的跨轮重叠或双缓冲。

### 4.3 关键约束

- 仅支持固定规格：
  - `A=[1024,2048]`
  - `B=[2048,2048]`
  - 输出均为 `[2048,2048]`
  - `rank_size=2`
  - `FP16`
  - `ND`
- 必须保留双输出：
  - 输出1：`A_gathered`
  - 输出2：`C`
- 必须保留由 `commTurn` 驱动的轮次处理结构；当前版本仅支持 `commTurn = 2`
- 不需要图模式
- 不需要特定架构实现
- `group` 作为既定配置项使用，不展开底层通信域实现

## 10. 风险与规避

### 10.1 双输出别名或覆盖风险
风险：
- `A_gathered` 与 `C` 地址重叠；
- `A_gathered` 被临时缓冲逻辑覆盖。

规避：
- 明确输出1和输出2为独立输出；
- 在接口与实现中禁止输出别名；
- 输出1作为最终 gather 结果，不作为可覆写临时区域使用。

### 10.2 两轮切分错误风险
风险：
- 每个 rank 的 512 行半块边界错误；
- 偏移计算错误；
- 当前 `commTurn = 2` 场景下的两轮处理范围交叉或遗漏。

规避：
- 固定采用“每个 rank 本地 shard 按 dim0 二分”；
- 每轮固定处理每个 rank 的 512 行；
- 所有偏移由统一 tiling 数据驱动；
- 按轮次和全局落位区间分别做测试验证。

### 10.3 Gather 落位错误风险
风险：
- 2 卡顺序写反；
- 本地块与对端块落位错乱。

规避：
- 以标准 AllGather rank 顺序为准；
- 使用易区分数据验证四段全局区间来源。

### 10.4 B 分块错配风险
风险：
- Round 0 读取了错误的全局区间 `B`；
- Round 1 读取了错误的全局区间 `B`。

规避：
- `B` 按与 `A_gathered` 完全一致的全局落位区间参与计算；
- 测试中四段区间填不同常量或模式值。

### 10.5 同步风险
风险：
- gather 数据未就绪即开始 add；
- staging buffer 在下一轮提前复用。

规避：
- 每轮建立明确同步点；
- 首版采用保守同步策略；
- 后续再逐步优化重叠。

### 10.6 workspace / buffer 生命周期风险
风险：
- 临时缓冲生命周期管理不清；
- workspace 被多用途混用造成覆盖。

规避：
- 首版优先简化 buffer 角色；
- 优先避免全量中间缓冲；
- 每轮只处理单块数据。

### 10.7 伪流水风险
风险：
- 实现表面上有“轮次”，实际仍是全量 gather 后统一 add。

规避：
- 设计和测试均要求按轮验证；
- 日志 / 调试点能够区分每轮边界；
- 评审时重点检查每轮是否形成独立处理单元。
